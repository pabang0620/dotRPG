# 지도 그림 용량·메모리·로딩 개선 (2026-10-11)

## 1. 실측

- 고해상도 지도 그림이 `StreamingAssets`에 PNG 그대로 1.1GB(지상 867MB, 지하 158MB) 들어가 빌드가 400MB 커졌다(APK 870MB -> 1.32GB).
- 지도 하나가 가로세로 6,000~9,000픽셀이고 그림 성격상 PNG 압축이 거의 안 된다(마을 58.7MB, 최적화해도 같음).
- 맵에 들어갈 때 PNG를 통째로 읽어 무압축 RGBA32로 푼다. 지도 하나에 메모리 160~226MB, 읽는 순간 원본 바이트와 픽셀 복사본이 겹쳐 400MB 이상. 마을 하나 PNG 해독만 PC에서 3.2초.
- 지하 맵은 HD 그림을 푼 뒤 같은 크기의 복사본 다섯 벌(원본 픽셀, 합친 그림, 층별 그림 3장)을 만들어 픽셀마다 나눈다. 지하 로딩이 느린 직접 원인.
- 맵 이동은 화면을 어둡게 한 뒤 위 작업을 메인 스레드에서 멈춘 채 처리한다(`GameFlow.TravelTo`).
- `sunken_sanctum`은 세로 9,216픽셀로, 8,192픽셀까지 받는 대부분의 폰에서 고해상도 그림이 뜨지 않는다.
- 픽셀 단위 계산 대부분(불투명 픽셀 수, 경계, 층별 일치 검사)은 개발용 점검(DevCapture)만 쓴다.

## 2. 조사 (상용 게임·엔진 권장)

- 큰 그림은 엔진이 GPU 압축 텍스처로 들고 있다가 그대로 GPU에 올린다. PNG를 실행 중에 푸는 방식은 쓰지 않는다. 모바일은 ASTC(블록 5x5~6x6 권장), PC는 BC/DXT 계열, 디스크 크기는 Crunch로 더 줄인다. 플랫폼마다 최대 크기를 따로 둔다(모바일은 작게). [Unity 텍스처 가이드, 텍스처 임포트 설정 토론]
- 불러오기는 비동기(Addressables·AssetBundle, 작은 규모는 Resources)로 하고, 로딩 화면은 실제 기다리는 동안만 보여 준다. 다 쓴 그림은 풀어 준다. [Unity 매뉴얼 Loading Resources at Runtime, Addressables 토론]
- 상용 게임은 처음에 전부 올리지 않는다. 공통 자원만 시작 때 올리고, 지역은 그때그때 또는 다음에 갈 곳(인접 지역)을 미리 올린다. 문·통로·화면 전환 연출로 기다림을 가린다. [Meta 오픈월드 스트리밍 가이드, Roblox 사례]
- "설치 후 처음 켤 때 내려받기/풀기"(Google Play Asset Delivery: install-time·fast-follow·on-demand)는 스토어(AAB) 배포용이다. 지금 같은 APK 직접 설치 시험에는 해당이 없고, GPU 압축 텍스처를 쓰면 풀 필요 자체가 없다. 출시 때 기본 용량이 커지면 그때 install-time 팩으로 나눈다.

## 3. 방향

1. **그림을 GPU 압축 텍스처로 바꾼다.** 지상 지도 PNG와 지하 합성 그림을 `Assets/Resources/WorldArt/`로 옮기고(git mv, 이력 유지), 임포트 규칙을 코드로 고정한다(`Editor/WorldArtImporter.cs`).
   - PC: 최대 16384, DXT1/DXT5 Crunch(품질 60)
   - Android: 최대 4096, ASTC 6x6. 폰 화면에서는 이 해상도로 충분하고, 8,192 초과 문제도 사라진다.
   - 읽기 가능(Read/Write) 끔, 밉맵 없음, Point 필터
2. **실행 중 픽셀 처리를 없앤다.** 지상은 이미 한 장의 텍스처 위에 층별 메시를 얹는 구조라 PNG 해독 대신 텍스처 에셋을 쓰면 된다. 지하도 같은 구조(한 장 + 층별 메시)로 바꿔 복사본 다섯 벌을 없앤다. 기둥 가림 처리는 다각형 메시로 바꾼다. 픽셀 통계는 개발용 점검에서만 쓰니 텍스처 에셋 경로에서는 건너뛴다(-1).
3. **불러오기를 비동기로 바꾸고 미리 올린다.** `MapArtCache`:
   - 맵 이동: 화면이 어두워진 동안 `Resources.LoadAsync`로 다음 맵 그림을 올리고, 끝나면 맵을 짓는다(이미 올라온 그림이라 즉시)
   - 도착 뒤 포털로 이어진 인접 맵을 백그라운드로 미리 올린다(PC 최대 4장, 폰은 1장)
   - 지금 맵, 직전 맵, 미리 올린 맵만 남기고 나머지는 푼다(`Resources.UnloadAsset`)
   - 게임 시작(캐릭터 선택 뒤) 때 현재 맵 그림을 먼저 올린다
4. **도구 경로 갱신:** `Tools/art/*.py`의 저장 경로를 새 위치로 바꾼다.

## 4. 예상 효과 (마을 기준 계산, 빌드 후 실측으로 확인)

| | 지금 | 바꾼 뒤 PC | 바꾼 뒤 폰 |
|---|---|---|---|
| 메모리 | 205MB(+순간 400MB) | 약 26MB(DXT1) | 약 7MB(ASTC 6x6, 4096) |
| 맵 진입 때 그림 준비 | PNG 해독 3초+픽셀 처리 | 텍스처 올리기(비동기) | 같음 |
| 빌드 안 지도 그림 | 1.1GB | Crunch로 수백 MB 이하 | 약 200MB |

## 5. 검증

- Unity 컴파일, PC·APK 빌드 크기 비교
- 개발 빌드 로그에 맵별 그림 준비 시간(ms)을 남겨 이동 시간 비교
- 화면 확인(그림이 제자리에 보이는지, 층 순서)은 사용자가 한다

## 6. 결과 (2026-10-11 빌드 실측)

| | 이전(v25) | 바꾼 뒤 |
|---|---|---|
| PC 빌드 폴더 | 1,435MB | 569MB |
| Android APK | 1,316MB | 375MB |

- APK가 크던 이유 하나가 더 있었다: Gradle은 이전 APK를 고쳐 쓰는 방식이라, 큰 파일이 빠져도 그 자리가 빈 공간으로 남았다(869MB 파일에 내용물 375MB). 큰 에셋을 옮기거나 지운 뒤에는 `-dotrpgCleanBuild`로 빌드한다(`BuildScript.CleanFlag`, Docs/ANDROID.md).
- 지도 그림 PC 첫 임포트(Crunch) 약 5분, 그림 한 장 6~13초. 이후에는 Library 캐시를 쓴다.
- 맵 이동 때 그림 준비 시간은 개발 빌드 로그 `[MapArt] <맵> ready in Nms`, 미리 준비되지 않은 경우 `loaded synchronously`로 확인한다.
- 화면 확인(층 위치, 지하 기둥 가림, 물 효과)은 사용자 확인 대기.
