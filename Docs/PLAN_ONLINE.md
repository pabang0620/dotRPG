## 1. 목표

| 목표 | 완료 기준 |
|---|---|
| 혼자서도 파티 | 사람이 없으면 AI 용병으로 빈자리를 채워 던전·레이드를 돈다 (이미 구현: 파티 기반 1단계) |
| 파티 구인 | 던전·난이도를 정해 파티를 모집하거나, 모집 중인 파티에 참가하거나, 자동 매칭한다 |
| 온라인 협동 | 최대 4명이 같은 던전 인스턴스에서 함께 싸우고, 보상·강화·드롭은 서버가 판정한다 |
| 빈자리 AI | 사람이 모자라거나 도중에 나가면 그 자리를 AI 용병이 이어받는다 |
| 서버 설계 | 계정, 캐릭터 저장, 로비·파티, 매칭, 던전 인스턴스, 경제 판정의 구조와 API가 문서로 정해져 있다 |

## 2. 플레이 흐름 (던파 방식)

```
마을 ─┬─ 던전 선택 창 ─┬─ [혼자 입장] ────────────── AI 용병 0~3명 편성 → 입장
      │                ├─ [파티 모집] → 모집 글 등록 → 참가자 대기 → 빈자리 AI → 입장
      │                └─ [자동 매칭] → 같은 던전·난이도 대기열 → 4명 또는 제한 시간 → 빈자리 AI → 입장
      └─ 파티 찾기 창(모집 게시판) → 글 목록(던전·난이도·인원·권장 전투력) → 참가 신청 → 방장 수락
```

- **파티 모집 게시판**(던파 파티 모집과 같은 역할): 던전, 난이도, 모집 인원, 최소 전투력, 한 줄 메시지. 목록은 던전·난이도 필터.
- **자동 매칭**: 같은 던전·난이도·권장 전투력 구간끼리 묶는다. 대기 60초가 지나면 모인 인원 + AI로 출발(설정으로 끌 수 있음).
- **파티 창**: 멤버 목록(사람/AI 표시, 직업, 레벨, 전투력, 준비 완료), 방장 위임, 강퇴, AI 용병 추가/제거, 입장 버튼(방장만).
- **던전 안**: 방 진행·부활·랭크·카드는 PLAN_DUNGEON_RAID §6.0과 같다. 카드는 각자 한 장씩 뒤집고, 자기 보상만 받는다(던파와 같음).
- **이탈**: 사람이 나가면 그 캐릭터는 AI 용병으로 바뀌어 끝까지 간다. 방장이 나가면 방장 권한이 다음 사람에게 넘어간다.
- **레이드**: 4인 파티, 주간 보상 귀속은 캐릭터별.
- **채팅**: 파티 채팅 + 빠른 신호(모여, 부활해 줘, 기믹 위치). 신고·차단은 서버 기획에 포함.

## 3. 클라이언트 구조 (지금 코드 기준)

### 3.1 이미 있는 것 (파티 기반 1단계, 커밋 453a9aa)
- 모든 파티원이 같은 `PlayerController`를 쓰고, 조작은 `IActorInput`으로 갈아 끼운다: `LocalInput`(키보드·패드), `CompanionBrain`(AI).
- `PartyManager`(`Game.Party`): 멤버 최대 4, Local, Leader, 쓰러짐·부활, 딜 미터, 어그로.
- 캐릭터별 스탯(`CharacterData`), `DamageInfo.attacker`로 킬 크레딧.

### 3.2 온라인용으로 추가할 것 (클라이언트, 서버 없이 만들 수 있는 부분)
- **ActorId**: 파티원마다 고유 id(계정 id + 캐릭터 id, AI는 파티 내 번호).
- **NetworkInput : IActorInput**: 원격 플레이어의 `ActorCommand` 스트림을 재생한다. 명령은 틱 번호가 붙은 작은 구조체(이동 방향, 조준, 버튼 비트, 스킬 슬롯).
- **권한 분리**: 막기 판정·드롭·강화·카드 보상·경험치처럼 결과가 남는 난수와 판정을 `IAuthority` 뒤로 모은다. 오프라인에서는 `LocalAuthority`(지금 방식), 온라인에서는 서버 응답을 기다리는 `ServerAuthority`.
- **세션 분리**: 오프라인 세이브(지금 JSON 슬롯)와 온라인 캐릭터를 나눈다. 온라인 캐릭터는 서버가 저장하고, 클라이언트는 받은 데이터를 표시만 한다.
- **가짜 서버(개발용)**: 같은 PC에서 창 2개를 띄워 테스트할 수 있는 로컬 루프백 전송. 서버 없이 동기화 코드를 검증하는 용도.
- **UI**: 파티 찾기 창, 매칭 대기 표시, 파티 창의 사람/AI 구분, 연결 상태·핑 표시.

### 3.3 AI 빈자리 규칙
- 입장할 때 사람이 4명 미만이면 방장이 고른 용병(없으면 역할이 겹치지 않게 자동 선택)으로 채운다.
- AI는 방장 클라이언트(또는 서버 인스턴스)가 계산한다. 다른 사람에게는 일반 원격 멤버처럼 보인다.
- 사람이 들어오면(던전 입장 전) AI 한 명이 빠진다. 던전 안에서는 교체하지 않는다.

## 4. 동기화 방식 (결정 필요, §6)

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 방장 권한 + 릴레이 | 방장 PC가 몬스터·판정을 돌리고, 나머지는 입력을 보낸다. 연결은 Steam 네트워킹 또는 Unity Relay | 서버 비용이 적고 빨리 만든다 | 방장이 조작할 수 있고, 방장 이탈 시 인계가 필요하다 |
| B. 전용 던전 서버 | 서버가 던전 인스턴스를 돌린다(Unity 헤드리스 빌드) | 던파처럼 치팅에 강하고, 공정하다 | 서버 비용과 운영 부담이 크다 |
| C. 혼합 (추천) | 전투는 A(방장 권한), **경제 판정(드롭·카드·강화·경험치·재화)은 백엔드 서버**가 한다 | 비용을 아끼면서 아이템 경제는 지킨다 | 전투 결과(클리어 여부)를 서버가 검증해야 한다(시간·딜 통계 이상치 검사) |

- 전송: 입력은 초당 20틱, 위치·HP 스냅샷은 초당 10회 + 보간. 스킬·피격·사망은 이벤트로 보낸다.
- 네트워크 라이브러리 후보: Unity Netcode for GameObjects + Unity Relay/Lobby, 또는 Steamworks.NET(Steam 로비·P2P). 출시 플랫폼이 Steam이면 Steam 쪽이 로비·친구 초대를 공짜로 준다.

## 5. 서버 기획 (구현하지 않음)

```
[클라이언트] ──HTTPS──> [API 게이트웨이] ─┬─ 인증 서비스 (Steam 티켓 / 이메일)
      │                                    ├─ 캐릭터 서비스 (캐릭터·인벤토리·창고·장비·강화)
      │                                    ├─ 경제 서비스 (강화 판정, 드롭, 카드 보상, 상점)
      │                                    ├─ 콘텐츠 서비스 (요일 입장 횟수, 레이드 주간 귀속, 초기화)
      │                                    └─ 파티·매칭 서비스 (모집 게시판, 매칭 대기열, 초대)
      └──WebSocket──> [실시간 게이트웨이] ── 파티 채팅, 매칭 알림, 파티 상태
      └──UDP(릴레이)─> [방장 PC] 또는 [던전 서버]
```

### 5.1 서비스별 책임
- **인증**: Steam 세션 티켓 검증 → 계정 생성·로그인 → 액세스 토큰(짧은 수명) + 갱신 토큰.
- **캐릭터**: 캐릭터 목록, 직업·레벨·스킬·패시브, 인벤토리(아이템 키 `기본id+강화` 그대로), 창고, 착용 장비. 모든 변경은 서버 트랜잭션.
- **경제**: 강화는 서버가 난수를 굴린다(확률표는 PLAN_DUNGEON_RAID §4와 같음). 드롭·카드 보상·경험치는 던전 결과 보고를 검증한 뒤 지급. 상점 가격도 서버 기준.
- **콘텐츠**: 요일·06:00 일일 초기화·목요일 06:00 주간 초기화를 **서버 시계**로 판정(오프라인과 달리 시계 조작 방지).
- **파티·매칭**: 파티 생성·참가·강퇴·방장 위임, 모집 글, 매칭 대기열(던전·난이도·전투력 구간), 입장 시 인스턴스 토큰 발급.
- **던전 결과 검증**: 방장이 보낸 결과(클리어 시간, 방별 처치 수, 파티원별 딜·피격)를 몬스터 데이터와 비교해 불가능한 값이면 보상 보류·로그.

### 5.2 데이터 (PostgreSQL 기준, 요약)
- accounts, characters, character_items(아이템 키·수량·위치: 가방/창고/착용 슬롯), character_progress(레벨·경험치·패시브·스킬), content_counters(요일 입장·주간 귀속·최고 랭크), enhance_logs, reward_logs, party_posts, match_tickets.
- 모든 로그 테이블은 추가만 한다(감사·CS 대응).

### 5.3 API 예시 (REST)
- `POST /auth/steam` → 토큰
- `GET /characters`, `GET /characters/{id}`
- `POST /characters/{id}/enhance` {target} → {outcome, newKey, cost}
- `POST /parties`, `POST /parties/{id}/join`, `POST /parties/{id}/start` → {instanceToken, relayInfo}
- `POST /match/queue` {dungeon, difficulty} / `DELETE /match/queue`
- `POST /runs/{token}/result` {stats} → {rank, cards}
- `POST /runs/{token}/cards/{index}` → {reward}

### 5.4 운영
- 서버 리전: 한국 1개로 시작. 매칭은 같은 리전끼리.
- 부정행위: 결과 검증, 강화·드롭 서버 판정, 클라이언트 세이브는 온라인 캐릭터에 쓰지 않음.
- 점검 공지·버전 체크: 접속 시 최소 클라이언트 버전 확인.
