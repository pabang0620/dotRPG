dotRPG(`/mnt/c/Users/admin/Desktop/games/dotRPG`)의 문서를 현재 구현에 맞춘다.

## 무엇이 정답인가
1. **코드·데이터가 정답이다.** 수치는 `server/data/*.json`, `Assets/Scripts/Runtime/**`의 상수(`[BALANCE ...]` 주석 포함), `Assets/Resources/Data/*.json`에서 읽는다. 문서끼리 다르면 코드와 같은 쪽으로 맞춘다.
2. 코드와 다른 문서 값이 **아직 구현 안 된 계획**이면(문서에 "예정", "초안", "N단계에서" 등) 지우지 말고 "현재 구현: X, 계획: Y"로 구분해 적는다.
3. 코드로 판정할 수 없는 충돌(방침·사업 결정끼리 충돌)은 **고치지 않고 보고**한다.
4. 사용자 결정 기록(`MASTER_CHECKLIST.md`·`PROGRESS.md`의 결정 표)은 내용을 바꾸지 않는다. 구현과 다르면 보고만 한다.

## 쓰는 방식
- 제출·공개용 문서(`STORE.md`, `README.md`)에는 수정 이력·"정정"·날짜 도장·재검증 과정을 쓰지 않는다. 현재 상태만 쓴다.
- 내부 기획 문서는 낡은 수치를 고치고, 필요하면 "(YYYY-MM-DD 기준 코드)" 한 줄만 단다.
- em-dash(—) 금지, 하이픈만. 문체는 기존 문서(평서형 "~다")를 따른다. 쉬운 말로 쓴다.
- 문서 전체 재작성 금지. 틀린 문장·표 행만 고친다.
- 스폰 프롬프트가 제외한 파일은 건드리지 않는다.
- 다른 게임 이름을 새로 쓰지 않는다(라이선스 검토 F6).

## 작업 순서
1. 스폰 프롬프트의 불일치 목록 항목마다: 관련 문서 문장 위치 → 코드·데이터의 실제 값(파일:줄) → 판정(문서 고침 / 계획 구분 표기 / 보고만)
2. 고친다.
3. 고친 수치가 다른 문서에도 있으면 `grep`으로 찾아 같이 고친다.

## 보고 (30줄 이내, 원문 인용 최소)
항목별: 문서:위치, 이전 값 → 새 값, 근거(코드 파일:줄). 고치지 않고 보고만 한 충돌 목록과 사용자가 정해야 할 것.
